**Date:** 25 September 2026
**Trigger:** client's explicit Slice 5 specification ("OLIVINE LIVE OPERATING MODEL — SLICE 5 — OPERATIONAL RECORDS, REVIEW, CORRECTION & CONTROLLED CRUD"), accepting Slices 1–4's delivery and building on it without redesigning or resetting it.
**Full analysis:** see `OLIVINE_LIVE_OPERATING_MODEL_GAP_ANALYSIS.md` Section 8 (rewritten in place across this slice) and `COMMAND_CENTRE_PROGRESS.md`'s new "Slice 5 consistency" section for the complete design record. See `CHANGELOG-olivine-live-operating-model-slice-4.md` for Slice 4, `-slice-3.md`/`-slice-2.md` for Slices 3/2.

## Summary

Users can now correct their own mistakes in the transport-cost pipeline without a database intervention. A person with normal operational access can edit non-financial fields (customer name, destination, invoice number, tonnage) on almost any record, cancel a record that should never post (with a required reason, kept as a permanent stamp — `cancelledAt`/`cancelledBy`/`cancelReason` — never a hard delete), and duplicate a record to re-enter a corrected copy. A person with finance-management authority can additionally correct a financial field (amount, date) on a record that has **already posted to the Allocation Ledger** — this reverses the existing posting and creates a new one for the corrected figure, exactly the way every other correction in this ledger already works, never a silent edit of a posted number. The Phase O2 identity-review queue (built in an earlier phase, functionally complete, but never reachable from the UI) now has its first-ever frontend. None of this is new financial machinery: every mutation here is a thin, permission- and state-checked caller in front of the SAME `AllocationService.reversePosting()` and `TransportCostPostingService.postSourceRecord()` this ledger has used since Slice 1 — this slice adds no new way to reverse or post money, only new, controlled ways to trigger the existing ones.

**This is additive and reuse-first, not a second CRUD system.** No new database, no new ledger, no new review queue. `TransportCostSourceRecord` gained exactly one behavioral concept (cancellation) and one provenance field (`duplicatedFromId`); its lifecycle status (`needs-review`/`ready-to-post`/`posted`/`reversed`/`cancelled`) is **derived at read time**, never stored — a deliberate decision to avoid a second, driftable source of truth sitting alongside the O2 review queue and the O3 ledger, which are the actual sources of truth this derivation reads from.

**The single most important correctness property of this delivery: a correction never double-counts.** `Correct` applies the patch to the source record, then calls the SAME `postSourceRecord()` every import batch already calls — which already, since Slice 1, detects an amount/currency change and performs a reverse-then-repost sequence. Reversing +1000 and posting +1200 nets to **+1200**, proven against the real reversal/posting engine (not a mock of it) with the exact worked figures, and additionally proven — new in this slice — through the Command Centre's own read path, which a person actually looks at, not just at the ledger layer.

**A genuine bug was found and fixed during this delivery's own test-first verification, before any of it was presented as done**, the same discipline Slice 4's changelog records for its own delivery. Editing a **REVERSED** (posted, then cancelled) record's financial fields was incorrectly refused with "cancelled by another request." Root cause and fix are recorded in full under "A bug found and fixed" below — flagged here in the summary because it is the kind of defect that would otherwise have shipped invisibly (a record would simply, silently, refuse to be corrected via Edit, forcing an unnecessary workaround), caught specifically by writing a test for an edge case the original implementation had not considered.

**No destructive database operation of any kind was performed or written. No historical data was touched, migrated, reset, or deleted. Every "delete" in this slice is `cancelledAt`/`cancelledBy`/`cancelReason` — a permanent stamp on a record that otherwise still exists in full — never a hard delete.** This is a pure additive change, following the same discipline as Slices 1–4.

## A bug found and fixed (documented plainly, not glossed over)

**What broke:** a test added for editing a **REVERSED** record (posted, then cancelled — see the state table) failed with `ConflictError: This record was cancelled by another request. Refresh and try again.` — even though `editSourceRecord`'s own business-rule check explicitly allows editing a reversed record (only `status === 'cancelled'` is refused).

**Root cause:** `conditionalUpdate`'s race-safety guard was `{cancelledAt: {$exists: false}}`, unconditionally, on every Edit. That guard is correct for its actual job — catching a genuine race where someone cancels the record between the status read and this write — for a record that has never been cancelled. But a **REVERSED** record's `cancelledAt` field IS already set (a reversed record was, at the raw-field level, cancelled; `deriveOperationalStatus` deliberately still reports it as `reversed`, not `cancelled`, because posting history exists and that history must never be hidden by a status name — see that function's own header). The guard didn't know this distinction and silently refused every edit to every reversed record, mislabeling a correct, intended write as a concurrency conflict.

**Fix:** the guard now asserts "`cancelledAt` is still exactly what we just read" — unset stays unset (still catches the real race against a concurrent Cancel), and an already-known `cancelledAt` on a reversed record is asserted to still equal itself (which it always will, since `cancelSourceRecord` already refuses to cancel an already-cancelled record — expressed as an explicit equality check rather than silently assumed). Fixing this correctly required the `fake-collection.ts` Date-equality fix above, since the two `Date` values being compared (one read moments earlier, one freshly re-read from the store) are equal in value but different JS object instances.

**How it was caught:** a deliberately adversarial edge-case test (`Edit on a REVERSED record`), written specifically because the state table calls out REVERSED as one of only two non-cancelled non-posted-financial-lock states, and because "the guard filter might not match the business rule" is exactly the kind of subtle gap a status-name-only review would miss. Caught and fixed before any of this was reported as done, with the full before/after test evidence in the commit history of this pass, not asserted from memory.

## Design decisions worth recording

- **Lifecycle status is derived, never stored.** `deriveOperationalStatus(source, hasPendingReview, postingHistory)` computes one of five states — `needs-review`, `ready-to-post`, `posted`, `reversed`, `cancelled` — from the O2 review queue and the O3 ledger's own posting history every time it's asked, rather than maintaining a sixth field that could drift from either of those two actual sources of truth. Two candidate states from the original brief (`DRAFT`, `CORRECTION_REQUIRED`) were deliberately NOT implemented — see `OLIVINE_LIVE_OPERATING_MODEL_GAP_ANALYSIS.md` Section 8.1 for the documented reasoning (no part of the actual workflow produces or needs either one).
- **REVERSED vs CANCELLED, in exact priority order.** `deriveOperationalStatus` checks posting history BEFORE `cancelledAt`: a record that was posted and later cancelled (reversed, no repost) must derive as `reversed`, never `cancelled`, because `cancelled` implies "this never had financial consequence" and would hide a materially important fact. This ordering is pinned by a dedicated test and is the exact property the bug above accidentally violated at the repository-guard layer (not the derivation layer, which was always correct) before being fixed.
- **Correct reuses the existing reversal engine; it does not reimplement it.** `correctPostedSourceRecord` applies the patch to the source record, then calls the SAME `TransportCostPostingService.postSourceRecord()` every import batch calls — which has performed the reverse-then-repost sequence since Slice 1 whenever it detects an amount/currency change. This slice adds a human-triggered CALLER of that existing behavior, not new reversal logic.
- **Concurrency without a version field.** This codebase has no optimistic-concurrency version field anywhere. `conditionalUpdate`'s atomic state-guard `findOneAndUpdate` is the same idiom the ledger's own idempotency index and `postSourceRecord`'s own `findReversalOf` recheck already establish, applied to `TransportCostSourceRecord` for the first time.
- **Least-privilege, checked once state is known.** No new permission was invented. `TRANSPORT_COST_VIEW`/`TRANSPORT_COST_NORMALIZE`/`FINANCE_MANAGE` are reused exactly as their existing scope already implies (view; touches operational data but not the ledger; can trigger a reversal or a posting). Cancel is the one genuinely state-dependent case: cancelling an unposted mistake is routine (`NORMALIZE`), but cancelling an already-posted record reverses a ledger entry and requires `FINANCE_MANAGE` — checked in the controller handler, once `getOperationalStatus` has actually been read, because the route wrapper cannot know the record's state in advance.
- **Bulk status, not N+1.** The operational table needed a per-row lifecycle badge. Computing it via one `getOperationalStatus` call per row would mean 20 extra queries per page load. Instead, `getOperationalStatusesForRecords` computes a whole page's statuses in a FIXED number of queries — one bulk review-queue lookup (`findPendingForSourceRecordIds`) plus at most one ledger lookup per distinct cost category present on the page (`findBySourceIdsForCategory`, already existed) — never one query per record. Proven with a spy-based test asserting each bulk repository method is called exactly once regardless of how many records are on the page.
- **`window.confirm`/`window.prompt`, not a new dialog primitive.** The original frontend plan (written before any frontend file had actually been read) proposed a new `ConfirmActionDialog` component. Reading `ExpenseListPage.tsx`'s existing `handleDelete`/`handleBulkDelete` surfaced the real, already-established convention: a plain `window.confirm`/`window.prompt` call, not a custom dialog. The plan was revised once that evidence was in hand — recorded as a reversal in `OLIVINE_LIVE_OPERATING_MODEL_GAP_ANALYSIS.md` Section 8.4, not silently substituted. Correct's richer "explain the financial consequence" requirement is satisfied by `EditRecordDialog`'s own body copy instead (a real dialog was needed regardless, for the amount/date form fields).
- **Frontend field-coverage scope, documented rather than silently narrowed.** `EditRecordDialog` exposes `customerName`/`destinationTown`/`salesInvoiceNo`/`tonnageRaw` (Edit) and `amount`/`date` (Correct) — the highest-value, safest-to-edit-via-a-plain-input fields of each backend-accepted list. `lines` (per-load editing) and the identity/company/periodization fields (`costFacingCompany`, `contractedVehicleId`, `transporterPartnerId`, `vansales`) are NOT yet exposed in the UI — a documented frontend surface-coverage gap, not a backend limitation (the backend endpoints already accept all of them).
