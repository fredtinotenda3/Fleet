# Role Responsibility Matrix

Who can do what, taken from `server/permissions/roles.ts` rather than
written from memory. Every cell below was generated by asking
`permissionService.hasPermission([role], permission)` for all 117
permissions and all 14 roles, so this document and the running system
cannot disagree.

Two things to hold in mind before reading it:

1. **A permission says WHAT. An org-unit assignment says WHICH.** Holding
   `fuel:create` does not let a branch manager log fuel for a Bulawayo
   truck — the write resolver checks the vehicle's org unit as well. See
   `SECURITY_MODEL.md`.
2. **`super_admin` is the only role that crosses tenants.**
   `organization_owner` is powerful inside one organization and must
   never be treated as a platform role: `AuthContext.isSuperAdmin` is
   true for both, which is why every platform endpoint checks the
   literal `Role.SUPER_ADMIN` instead.

## 2. The roles, in the words of the job

### `organization_owner` and `organization_admin`

Everything inside one organization: 110 of 117 permissions. The seven
they lack are the platform ones — reading across other customers is not
a privilege that exists inside a tenant.

> `AuthContext.isSuperAdmin` is **also true for `organization_owner`**.
> Every platform endpoint therefore checks `Role.SUPER_ADMIN` literally,
> and `PlatformController.requirePlatformAdmin` is the second of two
> guards for exactly this reason.

### `branch_manager` — accountable for a branch's cost per km

Full operational write over their branch: vehicles (not delete), trips,
fuel, expenses, maintenance. **Finance is read-only, deliberately** — a
branch manager must see their own cost per km, but posting depreciation,
submitting GL figures and changing finance settings are accounting
functions, not branch ones.

Can **assign and manage** a work order but not **create** one. That is
intentional: jobs arrive from a defect report or a maintenance reminder,
and a branch manager decides who does them.

### `fleet_manager` — the fleet across branches

The widest operational role after admin (60). Notably it can **complete**
maintenance and work orders, which `branch_manager` cannot, and it can
**move an org unit** (`org_unit:move`). It cannot delete a vehicle and
has **no trip write at all** — trips are recorded by the people who drive
and dispatch them.

### `workshop_manager` — the workshop, and only the workshop

Maintenance, work orders, bays, inventory adjustments, procurement
requests. **No fuel, no expenses, no trips.** A workshop manager opening
a vehicle's page sees the vehicle and its service history and gets no
"Log fuel" button, because the endpoint would refuse it.

### `department_manager` — a cost centre

Trips and expenses in full; fuel and maintenance read-only. This is the
role for a department that consumes fleet services and is billed for
them, rather than one that runs vehicles.

### `supervisor` and `dispatcher` — the day's work

Create and edit trips, assign drivers, run the dispatch board and the
shift roster. Neither can delete a trip: correcting today's board should
not be able to erase yesterday's history.

### `accountant` — the cost-per-km engine's owning role

The only non-admin role with `finance:manage`. Approves expenses, posts
allocations and depreciation, submits GL figures, exports analytics.
Records fuel and expenses because those are the transactions being
accounted for. **No vehicle, trip or maintenance write** — an accountant
does not run the fleet.

### `mechanic` — the person holding the spanner

Sees the vehicle and its maintenance, updates their own status, adjusts
stock as parts are consumed, and **completes** work orders and
maintenance. Cannot create either: a mechanic finishes work that was
assigned, and self-assigned work with no record of who asked for it is
how a workshop loses its cost trail.

### `driver` — creates, does not browse

Ten permissions. Can create a trip, log fuel, raise a DVIR defect and
request a booking; can read their own trips (`driver:view:trips`), the
vehicle list and maintenance. **Cannot read the fuel or expense list at
all** — a driver records their own refuel and does not see the fleet's
spending.

> This shape is why the onboarding checklist is gated on an ANCHOR
> permission set rather than on any single write. A driver holds
> `fuel:create`, so gating "record your first operating cost" on that
> permission alone presented a driver with a panel headed "Finish setting
> up your fleet" containing their ordinary daily work.

### `auditor` — reads everything, writes nothing

25 permissions, all reads plus `audit_log:verify` and
`analytics:export`. The only non-admin role that can read the audit log
and verify its hash chain. A conformance test asserts this role holds no
`:create`, `:edit` or `:delete` permission at all.

### `viewer` — nine reads

Vehicles, trips, fuel, expenses, maintenance, analytics, reports,
workflows, organization. Nothing else, and nothing that writes.

## 3. What the matrix does NOT decide

### Org-unit scope

A permission is necessary and never sufficient. Every write against a
vehicle resolves that vehicle under the caller's scope first
(`vehicleWriteResolver`), and since this round every write naming a
driver does the same (`driverWriteResolver`). A Harare branch manager
holding `fuel:create` still cannot record fuel for a Bulawayo truck, and
the refusal is worded identically to "no such vehicle" so it cannot be
used to enumerate another branch's fleet.

Reads follow the same rule from the other direction:
`tenantScopeService.buildFilter` narrows every list, and
`canAccessRecord` narrows every by-id read to exactly the same set.

### Records with no org unit

A record that carries no `orgUnitId` is reachable **only** by an
org-wide role. This tightened this round: five by-id loaders used to skip
the check entirely for such a record, so it was readable, updatable and
deletable by any authenticated holder of the permission while the list
hid it.

### Custom roles

`tblcustomroles` holds per-tenant roles that resolve within the same
tenant and combine with the static table above. The platform directory
returns a permission **count** for a custom role rather than its
contents — an allow-list projection, so a field added tomorrow is
omitted by default.

## 4. Two asymmetries worth knowing

**Fixed this round.** `branch_manager` and `accountant` held
`fuel:delete` without `fuel:edit`. The file's own policy note says a role
that can create and edit a record must be able to remove one entered in
error; these two could remove but not correct. Deleting is strictly the
more destructive option — it loses the audit trail and orphans the
record's allocation-ledger posting on an append-only ledger — so both now
hold `fuel:edit`, and
`tests/security/permission-symmetry.spec.ts` asserts no role anywhere has
delete without edit.

**Still true, and deliberate.** There is no `Permission.DRIVER_VIEW` or
`DRIVER_CREATE`. Driver management is gated on the `VEHICLE_*`
permissions as a stopgap, with only `driver:assign` and
`driver:view:trips` existing in their own right. The navigation and the
onboarding checklist mirror that stopgap exactly rather than inventing a
permission the API does not enforce. Introducing a real `DRIVER_*` set is
a backend change with a migration behind it.

## 5. Checking a role in practice

```bash
npm run test:security      # includes the permission conformance suites
```

To see exactly what a role holds:

```ts
import { Role, Permission, permissionService } from '@/server/permissions/roles';

Object.values(Permission).filter((p) =>
  permissionService.hasPermission([Role.BRANCH_MANAGER], p)
);
```

And when a user reports missing data, the permission is rarely the
answer — check the org-unit assignment first. A user with no assignment
is fail-closed by design: they see nothing.
