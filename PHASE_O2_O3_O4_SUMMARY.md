# Phase O2 / O3 / O4 — delivery summary

Built against the Phase O2 Spec and Phase O3 Spec tabs on the audit doc, and the confirmed decisions from the brief: currency handling seeded as a flagged provisional USD default, org-unit attribution left on O1's existing interim rule (not re-decided), fuzzy-match suggest-only, no hard joins across 3rd Party / Swift / PODs, no fuel or cost-per-km anywhere, `TransportCostPostingService` kept parallel to `AllocationService` rather than retrofitting `AllocationPosting`.

**This revision** closes out the six-item follow-up requested after the first delivery: an itemized rejected-rows report (§ Data quality), a Vansales periodization decision escalated rather than decided, a named Depot STO phase (`OLIVINE_PHASE_PLAN.md`), the `costCategory` split into three categories, `TransportCostPostingService`'s invariant-by-invariant comparison against `AllocationService` plus a parity test, a transport-cost-scoped `module-scope.registry.ts` completeness test, the O4 screen no longer showing a one-bucket "Unattributed" stream summary, and a data-quality exceptions CSV/JSON export. See "What changed in this revision" below for the full list; everything above "What shipped" describes the state as of the first delivery and is left as-is except where a later section says otherwise.

## What shipped

**Phase O2 — normalization review.** `ContractedVehicle` and `TransportPartner` master data, a shared `tblnormalizationreviewitems` review queue, and `NormalizationMatcherService` / `ConfirmReviewNewHandler` / `ConfirmReviewMatchHandler` / `RejectReviewItemHandler`. Every distinct transporter name and vehicle registration seen in an import is either matched against an existing confirmed identity or filed for a human to confirm as new or merge — the matcher never auto-merges a fuzzy candidate itself, only scores and suggests one.

**Phase O3 — posting to the Allocation Ledger.** `TransportCostVatConfigService` resolves currency and VAT basis per import batch or sheet family (batch-scoped confirmed → family-wide confirmed → provisional DEFAULT), and `TransportCostPostingService` posts each confirmed, amount-present 3rd Party source row to `tblallocationledger` under the `'third-party-transport'` cost category (see "The `costCategory` split" below) and `'tbltransportcostsourcerecords'` source collection, reusing the ledger's existing append-only/idempotency/reversal machinery. A correction (the source row's Amount changes after posting) reverses the old posting and posts a new one — the ledger never mutates a row in place, and a versioned idempotency key (`baseKey:v1`, `:v2`, …) lets a corrected row re-post without colliding with `tblallocationledger`'s unique `{tenantId, idempotencyKey}` index. `TransportCostPostingService` calls `allocationLedgerRepository.append()` directly rather than going through `AllocationService.postAllocation`, because that method's vehicle resolution is hard-wired to `tblvehicles` (Olivine-owned, telemetry-tracked vehicles) and would reject every contracted third-party vehicle; it safely reuses `AllocationService.reversePosting` for corrections, since that method never touches `tblvehicles`. The service's own header now documents, invariant by invariant, exactly what it reuses verbatim from `AllocationService`, what it deliberately skips, and what it deliberately replaces with a batch-safe contract — see "TransportCostPostingService vs. AllocationService" below.

**Phase O4 — the report/drill-down screen.** `TransportCostReportService.getAllocationReport` groups postings — postings only, never raw source records — by business stream and then by vehicle for a period, flags whether any of that period's rows are still pending an Amount, and refuses to sum two different reporting currencies into one figure. `getPostingsForVehicle` drills down to the individual postings behind one vehicle's total. `getDataQualityExceptions` (new this revision) surfaces rejected rows, duplicate-flagged rows, and period-outlier postings for a period — see "Data-quality exceptions export" below. The frontend is one screen: `/transport-cost/report` (`TransportCostReportPage`), a month picker defaulting to January 2026, Business Stream summary cards (hidden when the only stream present is "Unattributed" — see below), a Vehicle/Transporter table sorted by net amount, a pending-rows banner, an "Export exceptions" download, and a click-through drill-down dialog listing every posting (including reversals) for the selected vehicle.

## Hard constraints honored

- Never fabricates or zero-fills a missing amount, tonnage unit, or currency; renders `null` explicitly through to the UI (a pending-amount row posts nothing, and the screen's banner says so).
- No hard joins across 3rd Party / Swift / PODs. PODs is untouched.
- No fuel or cost-per-km logic anywhere in this slice.
- Fuzzy transporter/vehicle matching suggests only; `ConfirmReviewNewHandler`/`ConfirmReviewMatchHandler` are the only write paths that create or attach an identity, and both require an explicit human confirmation.
- `TransportCostPostingService` is a new, parallel service — `AllocationPosting`'s shape and `AllocationService`'s existing call paths are unchanged.

### 2b. Depot STO — named phase, phase plan added

**`OLIVINE_PHASE_PLAN.md`** is new: a table of every phase (O1–O4 shipped, Vansales posting blocked on the decision above, **O5 = Depot STO**, Swift/PODs not planned) with status and the reasoning for tracking Vansales and Depot STO as separate lines rather than one "remaining work" bucket. Depot STO's own schema/sourceCollection still do not exist — this document is what makes "deferred to O5" a real, findable commitment rather than only a code comment.

### 2c. The `costCategory` split

`AllocationCostCategory`'s single `'transport-cost'` member is now three: `'third-party-transport'` (live, what O3 actually posts), `'transport-retainer'` (reserved for Vansales, per 2a above), `'stock-transfer'` (reserved for Depot STO, per 2b above) — done now, while the ledger held zero real postings under the old category, so no migration was needed. Each is excluded from cost-per-km and filterable independently of the other two without a free-text match, so a future "how much did 3rd Party cost this month" query can never silently include a Depot STO stock movement or vice versa. `TransportCostPostingService`, `TransportCostReportService`, and the frontend's `COST_CATEGORY_LABELS` all updated; no reason found to keep a single combined category once the ledger was empty enough to split for free.

### 3. `TransportCostPostingService` vs. `AllocationService` — documented, not unified

Chose to document the invariant-by-invariant comparison plus a parity test, over extracting a shared vehicle-resolution seam. `TransportCostPostingService`'s header now spells out exactly what it reuses verbatim from `AllocationService`/`AllocationPostingService` (`resolveFxContext`, `roundCurrency`, `buildPostingIdempotencyKey`, and — most importantly — the real `reversePosting()` call for corrections, not a reimplementation), what it deliberately skips because the condition is structurally unreachable for this service (allocationRule quantity/unit/driver validation; periodEnd-before-periodStart), and what it deliberately replaces with a batch-safe contract (throw → skip on an unresolved FX rate/pending amount/unresolved identity, because `postImportBatch` must not abort a whole batch over one bad row). `tests/unit/transport-cost/transport-cost-posting.service.parity.spec.ts` (new, 3 tests) calls the REAL `AllocationService.postAllocation` and the REAL `TransportCostPostingService.postSourceRecord` against the same in-memory ledger and proves currency-uppercasing, amount-rounding, and FX-never-guesses behavior are identical — through the actual shared code, not asserted by inspection. Vehicle resolution itself (`tblvehicles`/org-unit-scoped vs. `tblcontractedvehicles`/organization-level) stays a documented, permanent divergence — unifying it would mean either fabricating a false org-unit ownership fact for a contracted vehicle or adding a polymorphic seam to `AllocationService`'s stable, safety-critical core to serve one category's different scoping model, which was judged riskier than one clearly-documented, tested exception.

### 4. `module-scope.registry.ts` completeness, enforced

All 6 transport-cost collections (the 5 from before this revision plus the new `tbltransportcostimportexceptions`) are registered in `module-scope.registry.ts`'s `'transport-cost'` entry. `tests/security/module-scope-conformance.spec.ts` now has a transport-cost-scoped test that scans every `collectionName = 'tblX'` literal under `modules/transport-cost/repositories/` and fails if any is unregistered — so a future collection added to this module and forgotten in the registry fails CI, not production. Deliberately scoped to this module rather than a codebase-wide check: a direct cross-reference found 18 pre-existing collections registered nowhere in the registry, all in modules this delivery never touched (expenses, notifications, oauth, reporting, rules, security, sla, telematics, server/events, server/scheduler) — a blanket check would fail on day one for unrelated reasons and get muted rather than fixed. That gap is real and recorded in the new test's own comment, but is out of this delivery's scope.

### 5. O4 screen: no more one-bucket "Unattributed" summary

`TransportCostReportPage.tsx`'s Business Stream summary cards are now hidden when `byBusinessStream` has exactly one entry and it is `'unattributed'` — which is every real month today (see the open item below), so the cards no longer restate the vehicle table below as a single tile that adds no information. They reappear automatically the moment a reviewer sets a real business stream on any vehicle, or a source reveals one.

### 6. Data-quality exceptions export

Rejected rows, duplicate-flagged rows, and period-outlier postings (the year-typo kind) are now **persisted and exported**, not just visible in a synchronous import response or a one-off verification script:

- `TransportCostImportException` (new type) is written by `ImportTransportCostHandler` for every rejected or duplicate-flagged row, best-effort (a logging failure never turns an already-decided row outcome into a thrown error or aborts the batch).
- `TransportCostReportService.getDataQualityExceptions(context, periodStart, periodEnd)` finds every import batch that produced a posting inside the period, then returns that batch's persisted exceptions (found by BATCH membership, not by the exception's own often-broken date — a row rejected for having no date must still be findable) plus any posting from those same batches whose own period falls outside the window (the general form of the January year-typo finding).
- `GET /api/transport-cost/report/exceptions?periodStart=...&periodEnd=...&format=json|csv` — same `TRANSPORT_COST_VIEW` permission gate as the report itself; `format=csv` returns a flat file (Kind/Import Batch/Source File/Row #/Raw Date/Raw Registration/Raw Transporter/Amount/Reason/Rejected Column/Invalid Value) mirroring `modules/attention/controllers/ledger-export.controller.ts`'s `?format=` convention.
- An "Export exceptions" button on `/transport-cost/report` downloads this CSV for the currently-selected month.
- `tbltransportcostimportexceptions` registered in `module-scope.registry.ts` (org-unit level, same rule as `tbltransportcostsourcerecords`) and indexed in `infrastructure/database/indexes.transport-cost-addendum.ts`.

## Swift import + posting (shipped after the Vansales slice)

Swift imports through one tolerant parser (`validateAndBuildSwift`) requiring only two columns per row — `Cons. date` (parseable) and `Cons. Number` (non-blank) — with every other column optional and preserved. Posts under `costCategory = 'third-party-transport'` (the same category 3rd Party posts under — Swift is structurally the same per-consignment transaction shape, not a retainer), `amount` from `Total(Incl)`, `date`/period from `Cons. date`. Full decision record, including why this needed a decision at all, in **`SWIFT_POSTING_DECISION.md`**.

**The structural finding that matters most:** the real "JAN-26 Swift" sheet has no registration/transporter column at all (verified directly against the workbook — nine columns, none of them a vehicle identifier). Since `AllocationPosting.vehicleId` is a required field, **a Swift row can import cleanly as source evidence but can never post to the ledger** — it always resolves to `{status: 'skipped', reason: 'unresolved-vehicle-identity'}`, via the exact same check a 3rd Party/Vansales row hits when its registration hasn't been confirmed yet. No new code was needed for that behavior; `resolveAmountAndPeriod`'s new `'swift'` case only had to supply the right amount/date. Neither a placeholder vehicle nor a schema change to `AllocationPosting` was made to work around this — both were rejected as fabrication/architecture-rewriting respectively. This is permanent, not a bug to fix later, unless Olivine's Swift export starts carrying a vehicle/transporter column or Olivine directs a different attribution rule (which would itself need its own Decision/Reason/Assumption/Reversibility entry).

**A second, smaller structural finding:** Swift rows are never flagged as likely duplicates. `findLikelyDuplicate` (pre-existing logic, written for registration-less Vansales rows) requires both a `registration` and a `date` to mean anything; since every Swift row's `registration` is always `null`, that check always short-circuits. Re-uploading the same Swift file twice will import every row twice as separate source records — this does **not** cause duplicate postings (idempotency is keyed off `sourceRecordId`, and every Swift row skips at posting regardless), only duplicate *source evidence*. Documented, not fixed, in `SWIFT_POSTING_DECISION.md` — inventing a different per-family dedup key was judged a real decision of its own, not something to guess at silently.

**Real January 2026 numbers:** 281 rows in the raw sheet (276 genuine consignments + 3 trailing blank rows + 1 blank row + Excel's own subtotal row). All 276 genuine rows import successfully (0 rejected among genuine rows, 0 duplicates); the 5 non-data rows are correctly rejected for missing `Cons. date`/`Cons. Number`. All 276 imported rows skip at posting for `unresolved-vehicle-identity`, so **$0.00 posts for Swift in January**, exactly as documented above — not a bug, a structural fact about the source data, reported transparently. The 276 genuine rows' own `Total(Incl)` sum ($30,588.62) matches the sheet's own trailing subtotal row to the cent, an independent cross-check that the row-level parsing is complete and correct.

Tests: 9 new (6 in `import-transport-cost.handler.spec.ts` — valid-row mapping, missing-Cons.-date rejection, missing-Cons.-Number rejection (the footer-row case), full-optional-column tolerance, raw-row provenance preservation, and confirming Swift never requires `periodMonth`; 3 in `transport-cost-posting.service.spec.ts` — amount/date resolution parity with 3rd Party, the universal `unresolved-vehicle-identity` skip for a real (vehicle-less) Swift row, and `pending-amount` refusal for a blank `Total(Incl)`). A pre-existing latent bug in `parseSourceDate`'s ISO-date branch was also fixed along the way (see below) — Swift is the first source family to actually exercise a genuinely Excel-date-typed cell through that code path. Full suite: 177/178 suites, 3,138/3,159 tests (up from 177/178, 3,129/3,150).

**Bug fix found and fixed during this slice:** `normalization.utils.ts`'s `parseSourceDate` used `new Date(aDateOnlyIsoString)` for its ISO branch, which the ECMA-262 spec defines as UTC-midnight parsing for a date-only string — silently re-introducing, one layer up, the exact previous-day shift that `shared/utils/excel-parser.utils.ts`'s `stringifyCell` was deliberately written to avoid (it converts an Excel date cell to `YYYY-MM-DD` using **local** getters specifically so a timezone west of UTC never sees the date roll back a day). Since 3rd Party's date cells are string-typed in the real workbook, this branch was previously "in case a re-exported template uses them" and effectively untested against real data; Swift's `Cons. date` column is the first genuinely Date-typed cell this pipeline has ever imported, so it's the first row to actually exercise the buggy path. Fixed by building the `Date` from the regex's own captured year/month/day digits (`new Date(year, month - 1, day)`, local midnight) instead of re-parsing the string — identical in shape to the pre-existing DMY branch, and verified against the real workbook's Swift dates (which carry an odd non-midnight time-of-day artifact from Excel's own serial-date storage — confirmed harmless either way, since only the calendar date is ever read back).

Verification run (`scripts/verify-phase-o3-o4.ts`, extended this slice): re-import-twice check passes (0 postings, 0 change in ledger row count across three runs — the correct "idempotent no-op" for a family that never posts, not just "no duplicates"); January 2026 Swift reconciliation against the workbook's own `Total(Incl)` sum (276 genuine rows, footer/blank rows correctly excluded rather than double-counted) shows **$0.00 unexplained residual**, with an explicit cross-check against the sheet's own subtotal row to confirm the row-level sum is complete.

## Depot STO / O5 import + posting (shipped after the Swift slice)

Depot STO imports through one tolerant parser (`validateAndBuildDepotSto`) requiring only `DATE` (parseable), covering the UNION of every column seen across **six real sheets, not four** — the real January 2026 workbook has March/April/May/June/July/August Depot STO tabs, not just "May–August" as a pre-existing doc comment assumed before this slice actually opened the workbook. Those six months turned out to be **four genuinely different column shapes**, not a single drifting layout: March/April share 3rd Party's own 8-column shape; May spreads quantity across five named per-product columns (`Golden Glow 2L`, `Olivine 2L`, `Puredrop 2L`, `Pure drop 5l`, `Pure Drop 750`) plus three sign-off columns; June/July replace those with a free-text `Commodity` plus `REG`/`DRIVER`/`TOONNES`; August drops `TOONNES`/`DRIVER`. Posts under `costCategory = 'stock-transfer'`, `DATE` used as-is for both `periodStart`/`periodEnd` (a dated stock movement, never a declared retainer month). Full decision record in **`DEPOT_STO_DECISION.md`**.

**Provenance, not interpretation — three separate raw-only fields.** The three named sign-off columns (`Mr Gurjit`/`Mr Inderjeet`/`Sharma Ji`, real values are booleans) are stored exactly as the source cell held them and never interpreted anywhere — no assumption about what `true`/`false` or presence/absence means for any of the three, per your explicit instruction. `TOONNES` (June/July's own literal spelling) is stored unconverted, kept deliberately separate from March/April's own different `Tonnage` column — the two are different real columns in different months' sheets, never merged. Neither is read by any computation yet, matching the pre-existing precedent for 3rd Party's own `tonnageRaw`.

**A gap caught and fixed before delivery: May's five per-product quantity columns.** An earlier draft of this slice modeled everything from `Amount`/`COSTS`/`COST` down to the sign-off fields, but left May's `Golden Glow 2L`/`Olivine 2L`/`Puredrop 2L`/`Pure drop 5l`/`Pure Drop 750` quantity columns out — on the mistaken assumption that `rawRow` (a spread of the row object) would "still preserve" them even without dedicated fields. That doesn't hold for a real upload: `ImportModal.buildRecordsForSubmission` only forwards the columns listed in a family's `ImportColumnDef[]`, so an unmapped column is dropped before the backend ever sees it. Caught and fixed before shipping: these five columns are unlike every other Depot STO drift (one column renamed per month) — several can be populated on the *same* May row simultaneously, so they can't fold into one canonical field the way `Amount`/`COSTS`/`COST` do. They're now their own `depotSto.mayProductQuantities: Record<string, number> | null`, keyed by each column's own literal header text, unconverted, never read by any computation — added to `DepotStoImportRow`/`DepotStoSourceFields`, `validateAndBuildDepotSto`, and the frontend's `DEPOT_STO_COLUMNS`.

**Vehicle-identity resolvability corrected before delivery, against the real data, not just the schema.** A first draft of this section (and matching code comments) reasoned from column *presence* alone: "March/April/June/July all have a registration-shaped column, so all four resolve a vehicle identity the same way as 3rd Party." Counting how often each month's registration column is actually *populated* in the real workbook told a different story, caught and corrected before shipping:

| Month | Registration column | Real rows | Populated | Resolves in practice |
|---|---|---:|---:|---|
| March | `Truck registration no` | 39 | 100% | Yes |
| April | `Truck registration no` | 33 | 100% | Yes |
| May | *(no such column)* | 55 | — | No (structural) |
| June | `REG` | 24 | 0% | No (data) |
| July | `REG` | 84 | 1.2% | No (data, in practice) |
| August | `REG` | 84 | 98.8% | Yes |

May's absence is a schema fact (no column exists). June/July's absence is a **data** fact — the `REG` column exists in the schema and the code correctly maps/resolves it when populated, but in the real January 2026 workbook it essentially never is. August was the surprise: it shares June/July's schema (minus `TOONNES`/`DRIVER`) but its `REG` column is populated in practice. No vehicle is ever fabricated to bridge either kind of gap — a structurally absent column and a present-but-empty one both produce the same honest `unresolved-vehicle-identity` skip. `DEPOT_STO_DECISION.md`, the posting service's header, the handler's header, and the row-shape doc comments were all corrected to state the real per-month rates, not the schema-only assumption.

**Duplicate detection** follows automatically from the table above: March/April/August rows (real registrations present) get ordinary `findLikelyDuplicate` checking; May/June/July rows (no usable registration in the real data) never trigger it — the same pre-existing "registration-less rows are never deduplicated" consequence already documented for Vansales and Swift.

**Real January 2026 workbook numbers, all six sheets combined:** 319 genuine data rows (March 39, April 33, May 55, June 24, July 84 — of which 72 have no DATE at all and are correctly rejected at import, not silently dropped — August 84), $308,429.00 combined Amount/COSTS/COST. 141 rows post to the ledger (March 36/$39,403.00, April 33/$36,942.00, August 72/$59,283.00 — total $135,628.00); the rest are explained by name: 11 genuine rows pending a blank Amount, 65 rows rejected at import validation ($75,363.00 — mostly July's undated rows), 14 flagged as likely duplicates ($5,399.00), and 92 rows skipped at posting for `unresolved-vehicle-identity` ($92,039.00 — May's 55, June's 21, July's 11, August's 1). **$0.00 unexplained residual.**

Full suite: 177/178 suites, 3,153/3,174 tests (up from 177/178, 3,138/3,159 after the Swift slice).

- **January 2026's business stream is "unattributed."** Verified directly against the source workbook: the January "JAN-26 3rd Party" and "JAN-26 Vansales" sheets carry no business-stream indicator anywhere (no per-stream tab split, unlike some later months, e.g. "MAY -26 3rd Party Olivine" vs. "...Hypery"; no explicit column). `ContractedVehicle.businessStream` is only ever set when a human reviewer supplies one while confirming an O2 review item — never inferred — so every vehicle first seen in January's data shows under "unattributed" until a reviewer sets a stream by hand, or a later month's data reveals it. This is the honest state of today's data, not a bug; the Stream → Vehicle hierarchy is fully built and will populate the moment a stream is actually known. The O4 screen no longer shows a redundant one-bucket summary card for this case (item 5 above), but the underlying attribution gap itself is unchanged.
- **Four source rows carry a year typo.** Rows 93, 96, 97, 105 on the January 3rd Party sheet have Date cells reading `30.01.25` / `31.01.25` (year 2025, not 2026) — Amount $642 / $688 / $1,070 / $260. The system parses a row's own Date cell literally rather than assuming the sheet tab's nominal month, so these four post correctly to January **2025**, not January 2026, and are absent from the January 2026 screen. Worth a one-line correction in the source file if these were meant to be `.26`. Now findable without this README via the exceptions export (item 6) and itemized in `DATA_QUALITY_REPORT_JANUARY_2026.md`.
- **Row 109's $33,906 figure.** New finding this revision, from the itemized rejected-rows report — a large amount with no date, registration, or transporter attached at all, immediately after the sheet's last real data row. Worth Olivine confirming whether this is a real delivery that lost its row data, or a stray figure that does not belong on this sheet. See `DATA_QUALITY_REPORT_JANUARY_2026.md`.
