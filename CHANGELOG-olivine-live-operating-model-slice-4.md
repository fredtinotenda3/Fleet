## Summary

Users can now open a single Cost Intelligence Command Centre (`/transport-cost/command-centre`) that answers, for any date range: how much transport cost was incurred, broken down by cost-facing company (Hypery/Olivine/Surface), cost category, vehicle, transporter, destination, and customer; how many operations and how many loads occurred in that period; and where the underlying data is incomplete, unresolved, or otherwise not analysis-ready. Every dollar figure on the page comes exclusively from the append-only Allocation Ledger; every operational count comes exclusively from source records; the two are never blended into a single number. Filters (date preset or custom range, company, category, vehicle, transporter, destination, customer) apply consistently to every KPI card, chart, and table on the page simultaneously, driven by one shared query.

**This reuses the existing reporting infrastructure — it is not a second reporting engine.** `TransportCostReportService`, `AllocationLedgerRepository`, and `TransportCostSourceRecordRepository` are extended with new methods following their own established patterns (bounded `findManyInScope` fetch + Node-side reduction, the same precedent `getDistinctPostedMonths` and the Slice A0 work already set); `ReportQueryEngine`/`DataSourceRegistry` (a separate, unrelated system confirmed during design) are not used anywhere in this delivery.

**The single most important correctness property of this delivery: a destination or customer filter can never multiply a financial total, however many lines an operation has.** The Slice 2 multi-line model (one parent operation → multiple lines → one parent-level cost → one ledger posting) is preserved exactly; nothing in this slice touches `TransportCostPostingService.resolveAmountAndPeriod`. A **filter** on destination/customer narrows which ledger postings are considered using OR-over-lines (a posting's source record matches if its own flat field OR any line matches) — safe, because it can only exclude non-matching records, and each record still contributes at most one posting either way. A **breakdown** (the byDestination/byCustomer tables and bars) buckets by the record's primary, line-1 field only, never by every distinct line value — because bucketing by every line would let one operation's single cost contribute to multiple bars, which is the exact "3 lines on one operation = $3,000 instead of $1,000" mistake the milestone explicitly warns against. A dedicated test asserts the byDestination/byCustomer bars always sum back to exactly the same `totals` figure, never more.

**A genuine bug was found and fixed during this delivery's own test-first verification, before any of it was presented as done.** The first implementation computed totals/breakdowns via separate ledger `$group` queries, narrowed — when a destination/customer filter was active — by a vehicle-id set derived from the destination/customer-matched postings. This is wrong whenever two different source records share a vehicle and only one of them matches the filter: both postings carry the same vehicleId, so an `$in` narrowing on vehicleId lets the non-matching one back in. The service's own test suite caught this immediately (a "filters by customer" test expected `100`, received `1099` — the full unfiltered total of two same-vehicle postings). The fix restructures the aggregation into a single Node-side reduction pass over the array of postings that has *already* been filtered/joined against source records (`matchedPostings`), rather than re-deriving any proxy set. This is documented in detail, inline, in `transport-cost-report.service.ts`.

**No destructive database operation of any kind was performed or written. No historical data was touched, migrated, or deleted. This is a pure additive change**, following the same discipline as Slices 1–3.

## Changed files

**Backend — ledger aggregation:**
- `modules/finance/repositories/allocation-ledger.repository.ts` — new `getNetTotalsGrouped(dimension, costCategoryScope, periodStart, periodEnd, context, filters)` (kept and independently tested as a generically useful grouped-totals method; **not** the code path `getCommandCentreSummary` actually uses — see the vehicle-id-proxy bug above for why); new `buildVehicleConstraint(vehicleId?, vehicleIds?)` helper giving `vehicleId`-single-value and `vehicleIds`-set filters correct **intersecting** semantics under one Mongo match key (a contradictory combination — e.g. a `vehicleId` not present in `vehicleIds` — now correctly resolves to `{vehicleId: {$in: []}}`, i.e. "no results," rather than one clause silently clobbering the other); widened `findRawByCategoryInScope` with a 5th, optional `extraMatch` parameter (`costFacingCompany`, `vehicleId`, `vehicleIds`), still bounded (`limit: 100000`) and still going through the same `getActiveFilter`/`tenantScopeService.buildFilter` tenant/org-unit scoping every other method on this repository already uses.

**Backend — source records:**
- `modules/transport-cost/repositories/transport-cost-source-record.repository.ts` — new module-level `matchesDestinationOrCustomer`/`hasAnyLineValue` helpers (OR-over-lines matching); widened `getLoadSummaryInScope` with a 5th `filters` parameter (`costFacingCompany`/`contractedVehicleIds` pushed into the Mongo match; `destinationTown`/`customerName` Node-filtered after the bounded fetch, since they must honor the line-array OR-semantics a flat Mongo filter cannot express safely); new `getDataQualityBreakdown(periodStart, periodEnd, context, sheetFamily[])` returning per-family-aware counts (`missingCostFacingCompany`, `missingRegistration`, `unresolvedVehicle`, `vehicleNotApplicable`, `unresolvedTransporter`, `missingCustomer`, `missingDestination`, `destinationNotApplicable`, `missingTonnage`) that correctly treat Vansales's lack of a destination field, and Swift's lack of a vehicle-registration field, as **Not applicable** rather than **Missing** — the family-specific "legitimate absence" distinction the milestone explicitly requires.

**Backend — service/controller:**
- `modules/transport-cost/services/transport-cost-report.service.ts` — widened `getDataQualityExceptions` to accept a cost-category-scope array (backward compatible — existing single-category callers, i.e. the O4 report screen, are unaffected); new types `CommandCentreGranularity`/`CommandCentreFilters`/`CommandCentreDimensionTotal`/`CommandCentreTimeSeriesBucket`/`CommandCentreDataQuality`/`CommandCentreSummary`; new helpers `bucketStartFor`/`bucketEndFor` (day/ISO-week-Monday-start/month bucketing), `CATEGORY_LABELS`, the `UNAVAILABLE`/`NOT_APPLICABLE` sentinel constants, `destinationBucketKey`/`customerBucketKey`/`bucketLabel`, `matchesDestinationCustomerFilter`, `resolveVehicleScope`, and `MAX_COMMAND_CENTRE_RANGE_DAYS = 400` (a sanity cap on custom ranges, preventing an accidental unbounded query); new `getCommandCentreSummary(context, periodStart, periodEnd, granularity, filters)` — validates the range (end ≥ start, ≤ 400 days, requested category within `TRANSPORT_COST_CATEGORIES`), fetches raw ledger postings once via the widened `findRawByCategoryInScope`, resolves their source records once, applies the destination/customer OR-over-lines filter once, then derives every dimension total and the time series from that single already-filtered array in one Node-side reduction pass (a shared `accumulate()` helper populating seven `Map`s plus the time-series map) — never via a second, separately-filtered ledger query per dimension, which is what the vehicle-id-proxy bug above came from. Operational counts and the data-quality breakdown are fetched independently, from source records, using the filter set established **before** the ledger join (so a destination/customer filter active with no vehicle/transporter filter does not incorrectly narrow operational counts to a ledger-derived vehicle set that has nothing to do with `getLoadSummaryInScope`'s own, correct, direct Node-side destination/customer filtering).
- `modules/transport-cost/controllers/transport-cost.controller.ts` — new `getCommandCentreSummary(req)`: parses and validates `periodStart`/`periodEnd`/`granularity` (must be `'day'|'week'|'month'`) and the optional filter query params, delegates to the service, returns `successResponse(result)`.

## Backward compatibility

- The O4 report screen (`TransportCostReportPage.tsx`) and its underlying `getAllocationReport`/`getNetTotalsByVehicleForCategory`/`COST_CATEGORY` (still pinned to `'third-party-transport'` alone) are completely unaffected — byte-for-byte unchanged numbers, unchanged single-category scope, unchanged behavior. `TRANSPORT_COST_CATEGORIES` (the widened array) is additive, used only by the new Command Centre code path.
- `findRawByCategoryInScope` and `getLoadSummaryInScope`'s new parameters are both optional with empty-object defaults; every existing caller (the O4 report path, the A0 work) continues to call them exactly as before and observes byte-for-byte identical behavior.
- No change to `TransportCostPostingService`, `AllocationService`, or any ledger write path. `AllocationLedgerRepository.update()`/`softDelete()`/`hardDelete()` continue to throw `ConflictError` unconditionally — re-verified explicitly by this slice's own security spec, including a spy confirming the new summary method never calls `.append`.
- No change to `TransportCostSourceRecord`/`TransportCostLine`'s shape. No new foreign key was added anywhere.

## Security/tenancy guarantee (structural, not just tested)

Every new repository method (`getNetTotalsGrouped`, the widened `findRawByCategoryInScope`/`getLoadSummaryInScope`, `getDataQualityBreakdown`) routes through the exact same `getActiveFilter`/`tenantScopeService.buildFilter`/`findManyInScope` machinery every other method on `AllocationLedgerRepository`/`TransportCostSourceRecordRepository` already uses — no new bypass path was written, and the fail-closed behavior on an empty `accessibleOrgUnitIds` array (`{orgUnitId: {$in: []}}`, confirmed empirically before this slice) is inherited automatically rather than re-implemented. This is proven directly, not assumed: the new repository specs include adversarial tenant/org-unit-exclusion tests, and the new security spec adds cross-tenant/cross-org-unit destination-and-customer-filter leakage tests specifically, since those are the two new filter dimensions this slice introduces. The route is `withAuth`-wrapped with `Permission.TRANSPORT_COST_VIEW` — the same read-only permission the existing O4 report route already requires, confirmed present and `TRANSPORT_COST_MANAGE` confirmed absent by a dedicated test reading the route file's own source, following `route-auth-conformance.spec.ts`'s established auto-discovery pattern.
