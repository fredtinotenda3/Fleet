# Decision: Depot STO (Phase O5) import shape, cost category, and provenance handling

**Status: SHIPPED.** Authorized in the user's 3-slice implementation instruction ("proceed to Depot STO/O5: use stock-transfer costCategory, DATE is the posting date as-is, preserve raw TOONNES in provenance and normalize only for computation, preserve the three sign-off fields as raw provenance only, do not invent their semantics, maintain the existing ledger and security architecture"). `ImportTransportCostHandler.validateAndBuildDepotSto` and `TransportCostPostingService.resolveAmountAndPeriod`'s `'depot-sto'` case are now live.

## What was found before writing any code (read this first — it changes the shape of this slice)

`OLIVINE_PHASE_PLAN.md` already flagged, before this slice started, that Depot STO's "column layout drifts month to month" and named it "May–August". Both of those things needed checking against the real workbook, not assumed from memory. Direct inspection of `TRANSPORT_COST_JANUARY_2026.xlsx` found:

- **Six months, not four**, each a differently-typo'd sheet name: `"march deport sto"`, `"APRIL- deport sto "`, `"MAY- deport sto "`, `"JUNE- deport sto  "`, `"july- deport sto   "`, `"august- deport sto   "`. March and April exist and were not previously accounted for in "May–August."
- **The layout doesn't just drift — it's four genuinely different shapes:**
  - **March/April**: `Date | Customer name | Transporter | Sales invoice no | Tonnage | Truck registration no | Destination Town | Amount` — literally the same 8 columns as the 3rd Party sheet (this was already anticipated in `ThirdPartyImportRow`'s own doc comment: "the '3rd Party' and 'Depot STO (March/April)' sheets... share this exact column set"). No `TOONNES`, no sign-off columns, no `STO`/`SOURCE`/`DEPOT` columns at all.
  - **May**: `DATE | STO | SOURCE | DEPOT | Commodity | Golden Glow 2L | Olivine 2L | Puredrop 2L | Pure drop 5l | Pure Drop 750 | Mr Gurjit | Mr Inderjeet | Sharma Ji | Transporter | COSTS` — per-product quantity columns instead of one tonnage figure, cost column named `COSTS`, no `TOONNES`, no `REG`.
  - **June/July**: `DATE | STO | SOURCE | DEPOT | Commodity | Mr Gurjit | Mr Inderjeet | Sharma Ji | Transporter | REG | DRIVER | COST | TOONNES` — the per-product columns are gone (replaced by a free-text `Commodity`), `REG`/`DRIVER` appear, cost column renamed again to `COST`, and this is the **only** shape that actually has a `TOONNES` column.
  - **August**: same as June/July minus `TOONNES` and `DRIVER`.
- **The three sign-off columns** (`Mr Gurjit`, `Mr Inderjeet`, `Sharma Ji`) only exist from **May onward** — March/April have no such columns at all. Their real values are **booleans** (`true`/`false`), not names, checkmarks, initials, or dates.
- **The cost column's own header renames four times**: `Amount` → `COSTS` → `COST` → `COST`.

This is materially more drift than Swift's (which kept a stable header set and only had optional columns come and go). The pre-existing `AllocationCostCategory` doc comment for `'stock-transfer'` said "May-August StockTransferRecord" — that was written before this slice actually opened the workbook; it undersold the real scope. That comment is corrected in this slice to "March-August" to match what the source data actually contains, since leaving March/April out of Depot STO coverage for no reason other than a stale doc comment would mean silently dropping two real months of source evidence.

## What shipped

**Decision:** One sheet family (`sheetFamily: 'depot-sto'`), one tolerant parser (`validateAndBuildDepotSto`), one canonical row shape (`DepotStoImportRow`) that is the UNION of every column seen across all six real months — every field optional except **`DATE`** (the only column present in literally every variant, and the one column the user's own instruction names as the posting-date anchor). `costCategory = 'stock-transfer'` (the category the codebase already reserved for exactly this, per Phase O3's category split). `DATE` is used as-is for both `periodStart` and `periodEnd` — no calendar-period inference, matching 3rd Party's and Swift's existing per-row dating convention, never Vansales's declared-month convention (a Depot STO row is a dated stock movement, not a retainer).

**Reason:** the six real months' headers never agree closely enough for a per-month parser variant to be worth maintaining (four distinct shapes in six months, two of them one-off), and the user's instruction explicitly rules out per-month parser variants for Swift on the same reasoning, which applies at least as strongly here. A single required column (`DATE`) is the only thing that survives every variant; everything else is optional and stored when present, matching the "reject with an explicit reason only for a genuinely missing REQUIRED column, tolerate everything else" philosophy already shipped for Swift.

**Cost figure:** stored under one canonical field, `amount`, regardless of which literal header (`Amount`/`COSTS`/`COST`) a given month's sheet used — the SAME "the operator/import-mapping step names the destination field, not the source month's literal header text" convention every other import family in this codebase already relies on (`ImportModal.buildRecordsForSubmission` matches an uploaded file's header against the destination `ImportColumnDef.key`, not the other way around; see the frontend section below). This is a naming/labeling decision, never a value decision — never sums or reconciles `Amount`/`COSTS`/`COST` figures against each other, since each row only ever has one of them populated for its own month.

**Sign-off fields — raw provenance only, semantics never invented.** `Mr Gurjit`/`Mr Inderjeet`/`Sharma Ji` are stored as a new `DepotStoSourceFields` nested object (mirroring `VansalesSourceFields`'s own convention) holding each column's literal value — `boolean | string | null` — exactly as it appeared in the source cell, with **no interpretation applied**: this code does NOT assume `true` means "approved," "signed off," "received," or anything else, and does NOT assume `false` means the opposite. Two reasons this stays deliberately uninterpreted: (1) the user's instruction says so explicitly ("preserve the three sign-off fields as raw provenance only... do not invent their semantics"), and (2) nothing in the audit, the workbook, or any prior conversation states what these three named individuals' role in a stock transfer actually is (dispatcher? receiving depot manager? finance sign-off? three sequential approval stages?) — guessing any of that would be exactly the kind of fabrication the hard constraints forbid. If Olivine ever explains what these three columns mean operationally, that's a new decision (e.g. "block posting until all three are `true`"), not a reinterpretation of already-stored data.

**May's five per-product quantity columns — corrected before delivery: preserved as their own field, not silently dropped.** An earlier draft of this slice's `DepotStoSourceFields` design left May's `Golden Glow 2L`/`Olivine 2L`/`Puredrop 2L`/`Pure drop 5l`/`Pure Drop 750` columns unmodeled, on the reasoning that `rawRow` would "still fully preserve" them. That reasoning didn't hold once checked against how a real upload actually reaches the backend: `ImportModal.buildRecordsForSubmission` only sends the columns listed in a family's `ImportColumnDef[]` (matched by header name), so a column with no destination field is dropped before the API ever sees it — `rawRow: {...row}` only spreads whatever the row object already contains, it can't recover a column nobody mapped. Caught and fixed before delivery: these five columns are unlike every other Depot STO drift (one column renamed per month) — they can all be populated on the SAME May row simultaneously, so they cannot be folded into one canonical field the way `Amount`/`COSTS`/`COST` are without losing real data. They're now stored as their own `depotSto.mayProductQuantities: Record<string, number> | null` object, keyed by each column's own literal header text, unconverted, never summed or read by any computation — the same raw-provenance-only discipline as `toonnesRaw` and the sign-off fields. `null` (not `{}`) for every non-May row.

**`TOONNES` — raw provenance, unconverted, no computation attached.** Stored as `depotSto.toonnesRaw: number | null`, exactly like 3rd Party's/Swift's own `tonnageRaw` fields — unconverted, because (per the original audit's Section K finding, still unconfirmed) whether a given family's tonnage figures read as kilograms or tonnes is inferred from value ranges, not confirmed by Olivine. "Normalize only for computation" — the user's own phrasing — currently normalizes to **nothing**, because no computation anywhere in this codebase consumes ANY family's tonnage field yet (3rd Party's `tonnageRaw`, stored since Phase O1, is not read by any report, cost-per-tonne calculation, or anything else — verified by grep). This is consistent with the existing precedent, not a new gap opened by this slice: the moment a real per-tonne computation is authorized, it would need to normalize `toonnesRaw` (and `tonnageRaw` for the other families) the same way, in one place, not per-family.

**Assumption:** the six real Depot STO sheets seen in the January 2026 workbook (March–August) are representative of the shapes this parser will ever need to tolerate. If a later month introduces a genuinely new required concept (not just a renamed/reordered/dropped optional column), that's a new decision, the same caveat already stated for Swift.
**Reversibility:** identical shape to every other decision in this project — a `DepotStoImportRow` field is additive and optional, so adding a new observed column from a future month's sheet is a small, isolated diff, never a breaking one. A posting made under `stock-transfer` reverses and re-posts through the existing `allocationService.reversePosting()` path like any other correction in this ledger.

## Vehicle identity — corrected against the real data, not just the schema

An earlier version of this section reasoned from column PRESENCE alone ("March/April/June/July all have a registration-shaped column, so all four resolve the same way as 3rd Party"). That was wrong, and the error was caught before delivery by actually counting how often each month's registration column is populated in the real January 2026 workbook, not just checking whether the column exists. The real per-month population rates:

| Month | Registration column | Real rows | Rows with a registration | Populated |
|---|---|---|---|---|
| March | `Truck registration no` | 39 | 39 | 100% |
| April | `Truck registration no` | 33 | 33 | 100% |
| May | *(no such column)* | 55 | 0 | — (structural) |
| June | `REG` | 24 | 0 | 0% |
| July | `REG` | 84 | 1 | 1.2% |
| August | `REG` | 84 | 83 | 98.8% |

So the real, evidence-based grouping is:
- **March, April, August** rows carry a real, populated registration in practice — resolvable via the existing Phase O2 normalization queue, same as 3rd Party. (August keeps a `REG` column, structurally identical in position to June/July's, but unlike June/July it is actually filled in for essentially every row.)
- **May** rows have **no registration column in the schema at all** — every row skips at posting time with `unresolved-vehicle-identity`, the same structural reason Swift's rows always do (see `SWIFT_POSTING_DECISION.md`).
- **June and July** rows have a `REG` column in the schema, but it is populated in essentially none of the real rows (0/24 and 1/84). These rows are **not** structurally prevented from carrying a registration the way May's are — `DepotStoImportRow.registration`/`validateAndBuildDepotSto` will map and resolve one if a future June/July-shaped sheet ever populates it — but for the real January 2026 data, they behave exactly like May: they skip at `unresolved-vehicle-identity` in practice, not by schema design but because the source rows themselves are missing the value. July's single populated row (1/84) is treated as ordinary data, not an exception worth special-casing.

No vehicle is ever fabricated to work around either case — a column that's absent by schema and a column that's present but empty in the data produce the identical, honest result: an `unresolved-vehicle-identity` skip.

## Duplicate detection

`findLikelyDuplicate` requires both a `registration` and a `date` to mean anything (the same pre-existing guard discussed in `SWIFT_POSTING_DECISION.md`). Given the corrected population rates above: March, April, and August rows (real registrations present) get ordinary duplicate detection. May rows (no registration column) and June/July rows (registration column present but essentially always empty in the real data) never trigger it — the same "registration-less rows are never deduplicated" consequence already documented for Vansales and Swift, now known to cover three of the six real months rather than two.

## Why "March-August", correcting the pre-existing doc comment

`modules/finance/types/allocation.types.ts`'s `AllocationCostCategory` doc comment for `'stock-transfer'` said "A Depot STO (May-August StockTransferRecord) movement" before this slice. That phrasing predates this slice's own direct inspection of the real workbook, which found March and April sheets too. The comment is corrected here to "March-August" — a documentation correction driven by evidence found while implementing, not a scope decision made unilaterally: the two extra months' data already existed in the source workbook and is handled by the same tolerant parser at no extra cost, so there was no principled reason to exclude them.
