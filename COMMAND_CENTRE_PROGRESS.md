**Design decisions worth recording:**
- **Financial vs. operational source of truth, kept strictly separate:** every dollar figure (`totals`, `byCompany`, `byCategory`, `byVehicle`, `byTransporter`, `byDestination`, `byCustomer`, `timeSeries`) is derived exclusively from `AllocationLedgerRepository`-sourced postings; every count (`operational.operationCount`, `.loadCount`, `dataQuality.*`) is derived exclusively from `TransportCostSourceRecordRepository`-sourced records. The two are never summed, joined, or blended into one number anywhere in `getCommandCentreSummary`.
- **Filter-vs-breakdown semantics (the core multi-line correctness design):** a destination/customer **filter** narrows which ledger postings are considered using OR-over-lines — a posting's source record matches if its flat field OR any `TransportCostLine` matches — which is safe because it only excludes non-matching records and each record still yields at most one posting. A destination/customer **breakdown** (the `byDestination`/`byCustomer` tables and their bars) buckets by the record's PRIMARY (flat, line-1) field only, never by every distinct line value, because bucketing by every line would let one operation's single cost contribute to multiple bars — the exact "3 lines = $3,000" mistake the milestone warns against. Verified by a dedicated test asserting `byDestination`/`byCustomer` bars always sum back to exactly `totals`, never more.
- **A genuine bug was found and fixed during this delivery's own verification, before anything shipped:** the first draft computed `totals`/`byCompany`/`byCategory`/`byVehicle` via separate ledger `$group` queries narrowed, when a destination/customer filter was active, by a `vehicleId` SET derived from the destination/customer-matched postings. This is wrong whenever two different source records share a vehicle and only one matches the filter — both share the vehicleId, so the `$in` narrowing lets the non-matching one through. Caught by the "filters by customer" test (expected `100`, got `1099` — the unfiltered total of two same-vehicle postings). Fixed by restructuring the aggregation into a single Node-side reduction pass over the already-filtered posting array (`matchedPostings`) directly, rather than re-deriving a vehicle-id proxy set. `getNetTotalsGrouped` remains in the repository (independently tested, generically useful) but is not on this code path. Full detail and the exact reasoning are inline in `transport-cost-report.service.ts`'s own comments and in the Slice 4 changelog.
- **Adaptive time-series granularity:** ≤21 days → day buckets, ≤120 days → ISO week buckets (Monday-start), else → month buckets — matching how long a user would realistically stare at that many data points.
- **No new indexes required or added:** every new query pattern is served by existing indexes from A0 and earlier slices (bounded `findManyInScope`/`findRawByCategoryInScope` fetches, `limit: 100000`, the same "bounded fetch + Node-side reduction" precedent `getDistinctPostedMonths` already established, needed because the test double's `.aggregate()` doesn't support the date-truncation expressions a native `$group` time-series would need, and adopted in production too for consistency with that precedent rather than diverging into two aggregation styles).

## Slice 5 consistency — what was verified and how

This is a **verification task, not a build task** (OLIVINE LIVE OPERATING MODEL Slice 5, task #62): once the Slice 5 Edit/Correct/Cancel/Duplicate commands existed (`TransportCostRecordCommandService`), the open question was whether this dashboard's own `getCommandCentreSummary` — built in Slice A, months before Slice 5 existed — would still report the right numbers immediately after one of those new mutations, given it reads the same `AllocationLedgerRepository`/`TransportCostSourceRecordRepository` Slice 5 writes to. No code in `getCommandCentreSummary` or its supporting repository methods was changed for this: the question was purely "do these two already-built things agree," not "does one of them need to change."

**New test file:** `tests/unit/transport-cost/transport-cost-slice5-command-centre-consistency.spec.ts` — wires `TransportCostRecordCommandService` and `TransportCostReportService` against the exact same in-memory ledger/source-record store (the same `jest.mock`-a-`FakeCollection` pattern this file's own Slice A tests use), then asserts:
- A fresh posting appears in `getCommandCentreSummary`'s net total immediately after `postSourceRecord`.
- A **Correct** (reverse + repost) shows the CORRECTED total in the Command Centre — not the sum of the original and the correction — with `postingCount: 3` (original + reversal + new), matching the exact worked-example invariant `transport-cost-record-command.service.spec.ts` already pins at the ledger layer, now additionally proven through the Command Centre's own read path.
- Cancelling an already-posted record nets its Command Centre contribution to an explicit **$0 across 2 postings** — a real, informative fact ("this net to zero, here's why") — never a fabricated empty "no data" row, and never silently dropped.
- Cancelling a record that was never posted correctly shows $0 in the FINANCIAL totals (there was never a posting) while still counting as 1 in the OPERATIONAL count (`operational.totalOperations`) — this dashboard deliberately keeps financial (ledger-sourced) and operational (source-record-sourced) numbers as two separate questions (see Slice A's own "Financial vs. operational source of truth, kept strictly separate" design decision above), and this is that same rule holding correctly under a Slice 5 mutation, not an inconsistency.

All 4 tests pass. Full-suite regression (`npm test -- --runInBand`) run immediately after: 189 suites / 3322 tests passing, zero regressions — see `OLIVINE_LIVE_OPERATING_MODEL_GAP_ANALYSIS.md` Section 8.5 for the complete Slice 5 test/verification account.
