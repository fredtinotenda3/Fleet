For Olivine. This is the itemized version of the "7 rows rejected at import validation" line in the reconciliation table — one line per row, not a count, so each one can be found and fixed (or confirmed as genuinely bad data) in the source file directly.

Machine-readable version: `GET /api/transport-cost/report/exceptions?periodStart=2026-01-01&periodEnd=2026-01-31&format=csv` (see the main delivery README's "Data-quality exceptions export" section) returns this same data as CSV, plus the 12 duplicate-flagged rows and the 4 out-of-period (year-typo) rows below, all three kinds together, filterable by the `Kind` column. This document exists so the same findings are readable without calling the API.

What this actually is, by row:

- **Row 24** — a normal-looking 3rd Party delivery (date, transporter, no Amount yet) missing only its registration. Likely a data-entry gap; fixable by filling in the registration.
- **Rows 87 and 102** — the Date cell has a **double period** (`27..01.26`, `31..01.26` instead of `27.01.26`, `31.01.26`). This is a typo, not a different date format — the parser accepts `DD.MM.YY`, `DD.MM.YYYY`, and ISO, and a stray extra `.` fails all three. Both rows otherwise look like complete, real deliveries (registration, transporter, amount all present) and are very likely one-character fixes.
- **Rows 107–110** — every field is blank except row 109's Amount (33,906). These four rows sit immediately after the sheet's real data (row 106 is the last populated 3rd Party row we found) and look like trailing artifacts of the spreadsheet — possibly a stray subtotal, a copy-paste remnant, or an accidental extra Amount entered with no corresponding row data. **Row 109 in particular is worth Olivine's attention**: a $33,906 figure with no date, registration, or transporter attached to it is either a real delivery whose row got corrupted, or a number that does not belong on this sheet at all (a subtotal, a different sheet's figure pasted in by mistake). It was correctly excluded rather than guessed into a fabricated row, but it is the single largest rejected amount and the one most likely to represent a real, missing transaction.

## 2. The 12 duplicate-flagged rows

Flagged by the soft duplicate check (same sheet family + registration + calendar date + amount as an already-imported row) — **not deleted, not merged**, just excluded from the posted total pending a human look. Total: **$627.00**.

Available in full via the CSV export above (`Kind = duplicate`); not re-listed row-by-row here since a duplicate-flagged row, by definition, restates a delivery that already appears elsewhere in this report under its original row — listing both would read as double the actual number of distinct deliveries in question. If Olivine's own records show these as 12 genuinely separate deliveries rather than 12 re-entries of an existing one, they should be reviewed and re-imported with a distinguishing note (destination, invoice number) rather than accepted as flagged.
