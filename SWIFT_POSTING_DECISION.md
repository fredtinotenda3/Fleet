# Decision: Swift import, cost category, and why Swift rows cannot post

**Status: SHIPPED.** Authorized in the user's 3-slice implementation instruction ("proceed to Swift: one tolerant parser, required-column subset, reject invalid rows with explicit reasons, costCategory = third-party-transport, preserve source provenance, do not create per-month parser variants, reconcile imported/postable totals against the source data"). `ImportTransportCostHandler.validateAndBuildSwift` and `TransportCostPostingService.resolveAmountAndPeriod`'s `'swift'` case are now live; see `PHASE_O2_O3_O4_SUMMARY.md`'s Swift section for the file list, test results, and the January 2026 reconciliation run.

## What shipped

**Decision:** Swift rows import through one tolerant parser (no per-month parser variants) requiring only two columns per row: `Cons. date` (must parse) and `Cons. Number` (must be non-blank — the closest thing this family has to "what makes this a real row, not a subtotal/footer"). Every other column (`Shipper reference`, `Receivers Name`, `Destination location`, `Actual weight`, `Total(Excl)`, `Tax amount`, `Total(Incl)`) is optional and stored when present, never required. Posted `amount` = `Total(Incl)` (the final, all-in settled figure, matching the same "post the total, not a component" reasoning as Vansales's `TOTAL`-over-`WEEK1`–`4` decision). `costCategory = 'third-party-transport'` — the same category 3rd Party posts under, because a Swift row is structurally the same kind of transaction (a dated, per-consignment charge), not a retainer.
**Reason:** the audit's original concern about Swift was schema drift month to month (the audit's Section B/S). A single tolerant parser over a small required subset absorbs an optional column being renamed, reordered, or dropped in a later month's sheet without a code change — only a genuinely required column's absence breaks a row, with an explicit per-row reason. `third-party-transport` (not a new category) avoids inventing a fourth `AllocationCostCategory` for a transaction shape the existing category already fits, per the "do not rewrite existing architecture" constraint.
**Assumption:** every Swift sheet, present and future, will keep at minimum a parseable per-row date and a non-blank per-row reference number — the two facts every real "JAN-26 Swift" row actually has. If a future month's Swift sheet lacks even those two columns, rows from it will be rejected with an explicit reason (never silently dropped, never fabricated), and this decision would need revisiting.
**Reversibility:** nothing here is a one-way door. The required-column subset is two `if` checks in `validateAndBuildSwift`; loosening or tightening it is a small, isolated diff. Re-pointing `costCategory` (e.g. if Olivine later wants Swift split out from 3rd Party in reporting) is one line in `COST_CATEGORY_BY_FAMILY` plus a migration of already-posted rows' `costCategory`, the same shape of change as any other cost-category correction in this ledger.

## Why a Swift row can be imported but can never post (this is structural, not a bug)

The real "JAN-26 Swift" sheet (verified directly against the workbook, not assumed) has exactly nine columns: `Cons. date`, `Cons. Number`, `Shipper reference`, `Receivers Name`, `Destination location`, `Actual weight`, `Total(Excl)`, `Tax amount`, `Total(Incl)`. **None of them is a registration or transporter identifier.** 3rd Party and Vansales both carry a `REG`/`registration` column that Phase O2's normalization queue eventually resolves to a `ContractedVehicle._id` (`contractedVehicleId`), which `AllocationPosting.vehicleId` (a **required** field — see `modules/finance/types/allocation.types.ts`) needs before any row can post.

Swift structurally has no such column to resolve. Two ways to "fix" this were both rejected as out of scope for this slice:
- **Fabricate a placeholder vehicle identity** (e.g. an "UNKNOWN — Swift" `ContractedVehicle` row) so every Swift posting has *some* `vehicleId`. Rejected: this invents a vehicle the source data does not support, exactly the kind of fabrication the hard constraints forbid, and it would silently misattribute cost to a fake entity in every vehicle-level report from then on.
- **Make `AllocationPosting.vehicleId` optional platform-wide** so a Swift posting can omit it. Rejected: this is a schema change to the shared, financially-safety-critical ledger type used by every other cost category, to serve one source family's missing column — exactly the "rewrite existing architecture" this task was told not to do, and it would weaken a real invariant (every other category's postings DO have a real, resolvable vehicle) for every other caller, not just this one.

**What actually happens instead:** a Swift row imports successfully (it is valid source evidence — date + reference number both present), but `TransportCostPostingService.postSourceRecord` will *always* return `{status: 'skipped', reason: 'unresolved-vehicle-identity'}` for it, via the **exact same check** a 3rd Party or Vansales row hits when its registration hasn't been confirmed through the Phase O2 normalization review queue yet. Zero new code was needed in the posting service for this specific behavior — `resolveAmountAndPeriod`'s `'swift'` case only had to supply the right `amount`/`date`, and the existing `if (!source.contractedVehicleId)` skip (which predates this slice) does the rest correctly on its own.

This is consistent, not intermittent: every Swift row, forever, until Olivine either (a) starts supplying a vehicle/transporter column in the Swift export, or (b) tells the platform Swift costs should be attributed some other way (e.g. to a single "Swift" pseudo-vehicle or cost center — which would itself need a Decision/Reason/Assumption/Reversibility entry, since it is a real attribution choice, not a technical default). Until then, Swift import gives Olivine full source-evidence visibility and provenance over Swift shipments, but Swift costs will not appear in the Allocation Ledger or the O4 vehicle-level report — this is reported explicitly (see the reconciliation section of `PHASE_O2_O3_O4_SUMMARY.md`), never silently.

## A second structural consequence, worth stating explicitly: Swift rows are never deduplicated

`TransportCostSourceRecordRepository.findLikelyDuplicate` requires **both** a `registration` and a `date` to mean anything (`if (!registration || !date) return null;` — a pre-existing guard, written for registration-less Vansales rows, reused here unchanged). Because every Swift row's `registration` is always `null` (see above — there is no column to populate it from), this guard always short-circuits for Swift: **no Swift row is ever flagged as a likely duplicate of another, no matter how similar.** Re-uploading the exact same Swift file twice will import every row twice, as two separate source records, not silently merged and not flagged.

This is the existing codebase's own established behavior for any registration-less row (the same thing already happens for a Vansales row with a blank `REG` cell), not new logic introduced by this slice, and changing it would mean inventing a different dedup key for Swift specifically (e.g. `consNumber`, which the audit's Section D join-key finding already shows has ~0 reliable cross-family overlap and was never validated as a safe per-family dedup key either) — a real decision, deliberately left open rather than guessed at here. Operationally, this means: **re-importing the same Swift export file twice will double-count source records** (though never double-*post*, independent of dedup — see the idempotency section below). The practical mitigation today is procedural (don't re-upload a Swift file that's already been imported), the same discipline already required for a registration-less Vansales row.

## Idempotency and correction are unaffected

`TransportCostPostingService.postSourceRecord`'s idempotency key is derived from `sourceRecordId` (the record's own `_id`, not any business key), so even in the above duplicate-import scenario, each of the two (now-duplicated) source records would independently and safely no-op on repeated `postSourceRecord` calls — the missing-dedup gap above is about **import-time row counting**, not about the ledger ever double-posting. And since every Swift row skips at `unresolved-vehicle-identity` today regardless, this gap currently has zero live financial impact — it would only start to matter once/if a future change lets Swift rows resolve a vehicle identity and actually post.
